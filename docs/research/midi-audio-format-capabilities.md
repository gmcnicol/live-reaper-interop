# MIDI CC and shared audio-format capabilities

**Research ticket:** [Establish MIDI CC and shared audio-format capabilities (#10)](https://github.com/gmcnicol/live-reaper-interop/issues/10).

**Retrieved:** 2026-11-17 UTC. **Runtime host tests:** none. **Status:** evidence gathering complete; the expanded milestone is **not proven feasible** through the proposed scripting routes.

## Scope and answer

The authority is the [agreed scope resolution](https://github.com/gmcnicol/live-reaper-interop/issues/9#issuecomment-6950250648), not this branch's older audio-only README/PROJECT_SCOPE. The target is fresh-destination interchange in both directions: editable notes with channels; timed CC with channels, including sustain; and original audio files readable by both installed hosts. Preserve non-grid starts, cuts, gaps, adjacency, names/order and repeated audio references. Polyphonic notes are in scope; arrangement overlaps, loops, warping, reversal, fades, instruments, routing and host automation are not. Unsupported content gets explicit omissions; unsafe or unrepresentable timing/source content must not be approximated. This note neither selects an adapter nor narrows that scope. [S]

**Findings:**

1. **REAPER has documented native ReaScript access to note timing/pitch/velocity/channel and CC timing/status/channel/data bytes, plus item boundaries and source offsets.** This is strong API evidence, not a successful round trip or a measured precision guarantee. [R1]
2. **Live has first-party Python note-API evidence, but no established arbitrary per-note channel field.** The documented note model and the inspected bundled-script implementation do not expose a channel in their note records. Ableton also documents channel-1-only ordinary internal MIDI routing. MPE output channel allocation is not preservation of original channel-tagged events. Required arbitrary note-channel fidelity is therefore a missing capability in the evidenced route, not something note support proves. [L1][L3][L4][P1][P2]
3. **Live's UI stores MIDI CC as clip envelopes, including sustain; a faithful Python CC event/channel import AND export path remains unknown.** Python device-parameter envelope operations are implementation evidence, but neither a controller-number/channel selector nor a lossless breakpoint/event enumerator is established by that evidence. Note APIs do not contain CC. CC 120–127 are unavailable in Live's MIDI Ctrl chooser. These are material gaps, not justification for silent CC loss or rejecting all MIDI. [L1][L4][L5][P3]
4. **WAV, AIFF, FLAC, Ogg Vorbis and MP3 are documented shared format families, subject to file attributes, host versions and decoders.** AIFF-C variants and macOS M4A need additional qualification. The claim is not “every file with these extensions works.” Live imports MP3/M4A/AAC through a decoded WAV cache; this is host behavior, not evidence that an adapter may convert or replace original media. Compressed-file source-zero, seek accuracy, cache-path read-back and save/reopen behavior remain validation gates. [R2][L6][L7]

### Notes and CC are different access paths

REAPER's typed note and CC APIs are distinct, with raw MIDI available for classification. A standard CC has status `0xB0 | channel`, controller and value; note-on/off, poly-aftertouch, program change, channel pressure, pitch bend and system messages are different protocol families. Therefore filter `chanmsg`/raw status before treating a REAPER “CC event” as a required controller event. Use raw inspection to find note-off/release information not represented by the typed note velocity field. [R1][M1]

Live's editable note API does not imply editable MIDI-controller envelopes through the same API. The inspected Python envelope example calls `clip.automation_envelope(parameter)`, `create_automation_envelope(parameter)`, `value_at_time(time)` and `insert_step(start,duration,value)` on device parameters. It demonstrates Python automation-envelope operations only; it supplies **no demonstrated method to select MIDI Ctrl CC64 on channel 2, list all CC breakpoints, preserve duplicate messages, or export their ordering**. Calling `value_at_time` at intervals would invent an approximation rather than recover the original event stream. [P3][S]

Likewise, Python `Live.MidiMap.forward_midi_cc` in bundled control-surface code routes **incoming controller messages** to a script; it is not evidence of reading/writing saved clip CC content. [P7]

Ableton's channel-1 routing help statement should not be expanded into “Live cannot receive 16 channels” or “MPE does not exist.” The same help page permits external input on all 16 channels; the MPE manual describes per-note expression and output zone/multi-channel allocation. Neither provides an original-channel field in the note API or independently channel-tagged controller envelopes. Splitting tracks, using MPE, adding a CC Control device, SMF exchange or directly editing Sets would be different approaches with their own fidelity/shape costs, **not fixes established or selected here**. [L4][L10][L1]

In particular, an SMF fallback is not an unqualified timing escape hatch: Ableton documents MIDI export as SMF0 at **96 PPQ**, shifting event positions to that grid. The cited support article is not a measurement of an installed build, but is enough to withhold a claim of arbitrary non-grid timing preservation through standard MIDI export. [L11]

### Event coordinates and clip boundaries: known units, unknown playback edge cases

- **REAPER:** item placement/length and take source offset are in seconds; event APIs use take PPQ. `MIDI_GetPPQPosFromProjTime`, `MIDI_GetProjTimeFromPPQPos`, and QN variants map between event and project coordinates. Use those mappings on the actual take rather than assuming PPQ zero equals the visible left edge or hard-coding a ticks-per-quarter value. `GetMediaSourceLength` reports whether source length is QN or seconds. Source sections/reversal have `GetMediaSourceParent` and `PCM_Source_GetSectionInfo`. [R1]
- **Live LOM:** note starts are absolute **clip** beat time, duration is beats; clip beat zero is the displayed 1.1.1. Arrangement starts are song beats. `end_time` describes the arrangement right edge. For MIDI/warped audio, `loop_start/end` are clip beats; for unwarped audio, they are seconds with zero at the source's first sample. `length` explicitly “makes no sense” for unwarped audio. `start_marker/end_marker` descriptions say beats; do not generalize those descriptions to unwarped source seconds without calibration. [L1]
- **Python evidence:** bundled clip controls write `loop_start/end` and `start_marker`, choosing a different control for looped/unlooped material. This establishes native property access in that implementation, **not** that changing those markers trims an Arrangement clip while holding its arrangement start fixed. [P6]
- **Hypothesis to test, not a schema decision:** for a non-looping MIDI source region beginning at clip beat `S`, placed at song beat `T`, an internal event at beat `q` would occur at `T + q - S`; at fixed BPM `B`, seconds would be that beat value × `60/B`. Check this against actual playback/read-back after each cut. For rate-1 audio, the analogous source time is `source_offset + (song_seconds - timeline_start_seconds)`. These are proposed validation equations, not evidence that either host preserves them automatically.
- **Unresolved semantics:** notes starting before a cut, note-offs beyond a right edge, CC state established before the visible region, events exactly at the right edge, same-time note/CC ordering and controller chase when starting transport inside a clip. Do not assume half-open intervals, crop hidden source events, synthesize note-ons/CC resets or lengthen sustained notes until the behavior and fidelity are established. Live's configurable **MIDI Envelope Auto-Reset** is a documented additional variable: Live 11.1 defaults it on for new Sets and off for older Sets. [L1][L3][R1]

### Unsupported MIDI content and reporting limits

Pitch bend, program changes, channel/poly aftertouch, release velocity, SysEx and MPE/per-note expression are outside this milestone even if a host can store them. Host automation is also outside it; MIDI CC is expressly **inside** it. Omit/report known unsupported events separately from required note/CC capability failures; skip an affected clip if its timing/content cannot otherwise be represented faithfully. Do not silently discard all MIDI because some events are unsupported. Invalid transfer data remains a blocker. [S]

REAPER raw events can distinguish the channel voice/system families; its text/SysEx API describes special handling of metadata and directs other cases to raw events. Inventory the raw stream as well as typed counts so notation/meta/expression/shape information is not mistaken for absence of unsupported data. [R1][M1]

Live's note fields can reveal probability, velocity deviation, mute and release velocity; its MPE manual documents expression dimensions outside this target. No complete native Python scanner for controller envelopes, SysEx or per-note expression was established here. If a future adapter cannot determine whether relevant data exists, that must be reported as **uninspectable**, not as a zero-count omission report. [L1][L10][P2]

Controllers 120–127 are channel-mode messages in the MIDI standard and are excluded from Live's MIDI Ctrl chooser. The agreed CC requirement did not grant a silent exception for them. Report the concrete controller and unavailable representation; do not invent a new scope exclusion. RPN/NRPN and 14-bit CC pairs also use CC messages; a list-of-CC representation alone is not evidence of correct compound-controller behavior or ordering after transfer. [M1][M2][L4][S]

### Original references, decoding, offsets and decoder delay

1. **Source references and cuts are separate from container decoding.** REAPER documents `GetMediaItemTake_Source`, `GetMediaSourceFileName`, source parent/section queries, `PCM_Source_CreateFromFile[Ex]`, `SetMediaItemTake_Source`, `D_STARTOFFS`, item position/length, and playback rate. None promises format-specific sample-exact seeking or uniform encoder-delay compensation. In-project MIDI need not have a source filename. [R1]
2. **Live's documented creation call takes an absolute path** to an audio file in a supported format and arrangement position; `file_path`, `sample_rate`, `sample_length`, markers and warping are documented LOM properties. The inspected Python exposure map includes file/marker properties, but does not establish direct Python audio creation in a named modern build. Unwarping can be deferred internally, according to the LOM; read it back on a later host turn before assigning unwarped source units. Exact source-slip plus independent arrangement-edge setters remain a host gate. [L1][L2][P2]
3. **MP3/M4A/AAC cache conversion is real.** Ableton says these files become temporary uncompressed WAV files in its Decoding Cache; cache size/free space can prevent import. The manual also describes compressed-file decoding more generally; it does not by itself settle whether every native FLAC/Vorbis import takes the same cache path. Host decoding/cache creation must not be confused with an adapter converting, collecting or replacing the original media. [L6][L7]
4. **Scope consequence, not a new decision:** no adapter-side conversion/rendering is authorized. For cached imports, validate that the original file stays unchanged and remains the reopenable source reference; record what Python `file_path` actually returns (original or cache) and whether it can recover the original. If only a cache-derived replacement is available, faithful original-reference transfer is blocked. If “no conversion” is interpreted literally to forbid even host-internal cache WAVs, MP3/M4A/AAC fail that condition by the published behavior; do not silently certify them under that interpretation. This research does not change that policy or reject other shared formats. [S][L6][L7]
5. **PCM/FLAC:** uncompressed sample frames offer a direct calibration reference; FLAC's specification is lossless, provides frame/sample numbering and permits sample-accurate seeking, even without a seek table (with potentially unpredictable seek latency). Those are **format facts**, not measured host accuracy or zero-latency seek promises. [F1]
6. **Vorbis:** the specification expresses granule positions in decoded PCM samples, with rules for discarding leading/trailing output and overlap across packets. A byte offset/page boundary is therefore not a source sample coordinate. Test seeks near stream beginning/end and packet boundaries instead of assuming arbitrary `.ogg` timestamps translate correctly. [F2]
7. **MP3:** LAME's technical FAQ explains encoder/decoder delay and frame dependencies. Its historical numerical examples are **not** universal host compensation constants. REAPER's official changelog records a **6.80** fix for off-by-one-sample initial MP3 decoding latency, **7.37** VBR index configuration, and earlier seek-accuracy fixes. This supports build/decoder-specific calibration, not a claim that current REAPER is inaccurate or a promise that it matches Live. [F3][R4]
8. **AAC:** Apple's packet-table documentation explicitly distinguishes valid samples, leading priming and trailing remainder frames, using 2112 priming frames only as an example. ALAC is lossless, not the same delay case as AAC. Neither source tells us whether the selected Live/REAPER decoder pair honors the same trim metadata, exposes the same decoded length, or seeks identically. **No fixed delay adjustment is established.** [F4][L7]
9. **Non-grid boundaries:** REAPER accepts item/source times as floating-point seconds; Live accepts beat-valued placement and unwarped second-valued source markers in its LOM. These types do not guarantee sample-accurate edges, nor that a lossy source's source-zero corresponds to the pre-encoding PCM zero. Measure each independently after reopen. [R1][L1][L2][F3][F4]

No conversion, consolidation, collected-media copy or guessed delay correction should be used to turn a failed format probe into a “pass.” Format-specific failures should leave other faithfully representable clips available, with explicit item/file diagnostics; unresolved required media remains blocking under the scope. [S]

Make the visible cuts with ordinary host trims, logging item position/length, take start offset, loop flag and the PPQ↔project mappings before/after. Do not assume all source events disappear when trimming an item. [R1][M1]

### 3. Audio fixture and decoder calibration

Prepare and retain an immutable **10-second, 48 kHz, stereo PCM reference** (480000 frames). Place single-frame impulses at zero-based frame indices 0, 1, 529, 1153, 48001, 96007, 144013 and 479998: left amplitude +0.75, right amplitude −0.25, with zeros elsewhere. Record the exact generator/settings and SHA-256. Create **test assets only**, not bridge conversions: PCM WAV/AIFF (16/24-bit), float WAV, native FLAC with/without seek table, Ogg Vorbis, MP3 CBR/VBR with encoder delay/padding metadata and a controlled copy without it; on macOS also AAC-M4A and ALAC-M4A. Record encoder/build/options and hash each file. A known existing encoder/asset pipeline is a prerequisite; do not install or invoke one during this research. Include representative 44.1 kHz assets to separate sample-rate conversion from offset errors. [F1][F2][F3][F4]

- On **each installed host**, import each original encoded file independently. Record actual decoder/backend, returned file path, source length/rate/channels and import errors; compare with the publisher matrix. Use supported PCM WAV as a control, not the only accepted format. Include deliberate failures: Opus, Ogg-FLAC, unsupported AIFF/WAV subtypes, `.aifc`, >2-channel input and a damaged file. No auto-renaming, conversion or downmix may turn failure into success. [R2][L7][S]
- First establish each host's **full decoded reference** by measurement/capture with effects, fades, warp, transpose and normalization off. For lossy assets, assess relative transient timing/alignment, not bitwise identity to the pre-encoding PCM impulse. Record leading/trailing trim and decoded frame count before testing arbitrary seeks. This separates codec change from source-offset error.
- Use source offset **96007/48000 s**, visible duration **50003/48000 s**, arrangement start **123457/48000 s**. Set rate 1. Place a second clip exactly at the first's end and a third, gapped clip referencing the same original. These boundaries deliberately avoid musical grid and typical packet/frame alignment. Repeat with offsets near zero (0, 1, 529, 1153 frames), around further packet/frame boundaries and near EOF, with durations staying inside the decoded source.
- REAPER: read/write item `D_POSITION`, `D_LENGTH`, take `D_STARTOFFS`, `D_PLAYRATE`; set `B_LOOPSRC=0`, inspect source type/parent/section, and compare source filename before/after. Gate source creation/assignment failures and inspect actual decoded samples, e.g. `CreateTakeAudioAccessor`/`GetAudioAccessorSamples` (documented pre-FX sample access), rather than using only peaks or an extension whitelist. [R1]
- Live: from Python test `create_audio_clip(path,position_beats)` only if present; map each independent arrangement edge from seconds using 120 BPM. Read `warping` back after the deferred change settles, then log `file_path`, sample rate/length, loop/source markers and arrangement edges before/after every source-offset/trim operation. Use unwarped source-second markers, not `length`, for the source-region experiment; precisely log attempted setters and whether they fail, move, slip or trim. A successful UI import is not proof the Python creation route can do it. [L1][L2]
- Play from the beginning, jump directly to each cut and repeatedly seek backward/forward; compare the first audible/captured transient to that host's full decoded reference and then across hosts. Record requested and actual sample index, offset error, start/end error and seek settling time. Avoid calling device/output latency “decoder delay”; calibrate the capture path independently or use host offline diagnostic capture. Diagnostic renders are measurements only, never replacement interchange sources.
- Save/reopen and repeat in both directions into fresh destinations. For MP3/M4A, inspect whether `file_path` and saved references name the original or the cache WAV. With Live closed, remove **only disposable cached fixture entries** (never original media or unrelated cache entries), reopen and test regeneration. Record disk-full/cache failure separately if safely reproducible in an isolated test location. Hash originals again; expect no changed source bytes. Cache regeneration must not change source-zero, cuts or the usable original reference. [L6][L7]
- Repeat on every claimed OS/build/decoder combination. Do not extrapolate Windows Live 12 MP3 behavior to Windows Live 11, macOS M4A to Windows, or native FLAC to Ogg-FLAC. [L7]

### 4. Result record and pass/fail interpretation

For every subtest retain: host/OS/interpreter/decoder versions; fixture hash and original path; API route and units; expected source/timeline/event values; actual before/after/reopen values; exceptions; MIDI raw capture or audio alignment measurements; omissions/uninspectable data; neighbor snapshots; and recovery/undo outcome. No API should mutate the original source projects/media; use only disposable destinations. [S]

- **A passing supported MIDI clip** must preserve editable pitch/onset/duration/velocity **and original channels**, plus timed CC/controller/value/**channel**, with sustain still independent CC. A chord alone, a clip whose CC was omitted without a report, or correct playback through a remapped instrument does not establish that. [S]
- **A passing audio file/host pair** needs successful original-file reference/reopen, correct source segment and independent timeline cuts; accepted extension or matching marker numbers alone is insufficient. Record measured precision. The old plan's one-source-sample target is a useful calibration challenge, **not an established guarantee or a newly fixed contract tolerance**.
- For lossy media distinguish encoder-induced waveform change from a consistent seek-origin mismatch. A mismatch must be reported; no guessed constant-delay correction or automatic transcode. If faithful timing/source content is not possible, skip the affected item with a clear reason while keeping independently valid items eligible. Unresolved required media/invalid data and unsafe destination operations are still blockers. [S]
- Persistence passes only after full host close/reopen and new enumeration/read-back. Record normalization rather than asserting runtime note IDs are durable project identities. Existing-project update/merge/idempotence remains outside this ticket. [S]

## Blockers and handoff

1. **Required Live per-event channels:** no original-channel field in the evidenced ordinary note representation; ordinary channel-1 routing and separate MPE allocation are not sufficient. A full arbitrary-channel round trip is **not established**. [L1][L4][L10][P2]
2. **Required Live CC:** Python creation/export/read-back of timed CC with channel, controller and value is unestablished; available parameter-envelope calls do not close the gap. CC120–127 have an explicit UI representation limit. Complete unsupported-event detection is also unestablished. [L4][P3]
3. **Live arrangement/source-boundary control:** direct modern Python clip creation, independent arrangement cuts/source offsets, edge-event playback and neighbor safety require the named-build experiments above. Max-only API additions cannot discharge this. [L1][L2][L8]
4. **Shared audio qualification:** installed decoders, format variants, cache/original path identity, decoder-delay/seek equivalence and reopened cuts are untested. MP3/M4A have documented cache conversion; the bridge must not silently substitute converted media. [L6][L7][R4]
5. **No host execution in this Linux worker:** no exact target versions/editions or measured timing tolerances, event fidelity or persistence results. The procedures above are the reproducible handoff, not passed acceptance tests.

Evidence gathering can close #10 with these explicit gaps. It does **not** resolve the human adapter choice, prove feasibility, authorize an audio-only downgrade, define the final contract, or require rejection of every clip/format. No production implementation or other ticket resolution is part of this artifact. [S]
