# REAPER arrangement timing and identity capabilities

Research for [ticket #4](https://github.com/gmcnicol/live-reaper-interop/issues/4), under [the interchange map](https://github.com/gmcnicol/live-reaper-interop/issues/1).

**Retrieved: 2026-11-17 UTC. Investigation complete; host feasibility is not proven.**

## Answer and evidence boundary

REAPER documents native ReaScript operations for creating tracks, items and takes; attaching file sources; setting timeline position, length and source offset; and converting project time to quarter notes. This supports a **conditional fresh-destination route**, without requiring RPP editing, SWS or rendering. It does not establish audible correctness, sample accuracy or cross-host feasibility. See the cited matrix below.

For an existing-project update, the strongest explicit persistence contract found is project extension state saved inside the RPP and restored on project loading. Item, take and track APIs also expose writable GUIDs and extension-specific persistent data. Those entries do **not** specify a complete GUID or custom-tag lifecycle for saves, splits, duplication, copying between projects, undo or independent edits. Do not promote their existence into a guaranteed bridge identity strategy. [Project persistence][sdk-persistence] [Project extension state][projext] [Item strings][itemstrings] [Take strings][takestrings] [Track strings][trackstrings]

Evidence labels:

- **D — documented:** explicit statement or signature in an owning primary source.
- **I — inference/recommendation:** a proposed use of those APIs, not observed host behaviour.
- **U — unresolved:** the consulted sources do not settle the requirement.
- **R — runtime-tested:** actual REAPER execution. **No R evidence was obtained. Every host procedure below is unrun.**

The supplied environment report found neither host in shallow installation checks. This investigation independently confirmed neither `reaper` nor `wine` is on PATH. That blocks execution here, not research, and says nothing about the human's other machines. No host, extension, dependency or service was installed. Repository README and scope documents were read as hypotheses, not capability evidence.

The entries above document **access and storage**, not a whole-project merge algorithm. Their writable GUIDs also mean an adapter cannot assume uniqueness in arbitrary projects produced by other scripts. **Recommendation (I):** fresh imports can use transfer-local occurrence IDs and retain a source-host GUID as provenance. Existing-project updates need a separately validated association strategy and baseline; project state and `P_EXT` are candidates, not a decision to implement a sidecar or tag scheme. A project-state lookup table does not discover which split or duplicate inherited which entry. Do not overwrite native GUIDs to manufacture continuity. Do not use file paths, shared source recordings or matching geometry as automatic item correspondence.

Runtime pointers are also not stored IDs: `ValidatePtr2` checks whether a pointer is currently valid and belongs to a project; its entry does not promise survival across deletion, reload or undo. Reacquire objects after those events. `GetProjectStateChangeCount` changes with project state; it is not documented as a persistent revision ID or conflict history. ## Timing and precision limits

1. **D:** item coordinates, take offsets, source duration and time-map conversions use C `double`/Lua `number` interfaces. Source rate is a separate integer; source length may instead be in QN. None of the cited entries gives a sample-accuracy bound, persistence rounding guarantee or maximum reliable timeline duration. [Items][itemvalues] [Takes][takevalues] [Length][sourcelength] [Rate][sourcerate] [Conversion][toqn]
2. **D, narrow source-code evidence:** the SDK's `ADVANCE_TIME_BY_SAMPLES` macro uses seconds arithmetic and comments “not completely accurate but still quite accurate.” This is a warning about that helper, **not evidence that the item setters use it**, and not a measured interchange error. [PCM SDK helper][sampleadvance]
3. **I:** do not round to UI time strings, beats, video frames or milliseconds. Preserve round-trippable numerical values, and distinguish timeline seconds, source sample frames and QN. Measure start and end separately; duration-only checking can miss a shifted item.
4. **I:** for a known fixture rate `S`, compare `abs(actual_seconds * S - expected_frame)` for start, end and source offset. Report the raw seconds and fractional-frame errors, not only rounded frame indices. A one-frame tolerance is a proposed acceptance gate, not a result. Also report adjacency gap/overlap independently.
5. **I/U:** source frame count computed from seconds is derived metadata. For a direct normal-rate PCM source, validate `offset >= 0` and `offset + length <= source_duration`, with a deliberately specified numerical tolerance later. Wrappers, loops, rates and stretches require other mappings and stay rejected.
6. **I/U:** one constant tempo does not remove source/project sample-rate differences, master playrate, display-origin or item-timebase questions. Initially use matching source/project rates and a zero origin in the fixture. Mixed-rate sources and nonzero origins need separate evidence before inclusion. No audible or bit-identical guarantee is made.

## Minimal real-host validation procedure — not run

This is a disposable capability experiment, not an adapter or a schema. Run only on copies and generated media. Keep originals untouched. A later operator needs REAPER with Lua on an actual machine; this environment cannot execute it. Cross-host results belong to the separate Live and combined-host investigations.

### 1. Record the environment and build known media

Record OS/architecture, REAPER full `GetAppVersion()`, Lua `_VERSION`, project/device sample rates, tempo/signature, project-start offset, master rate, auto-fade settings, item timebase and installed extensions. Record `APIExists` results for every function used. Do not infer a supported OS/version matrix from one run. [Version][appversion] [API check][apiexists] [Project][projectvalues] [Offset][timeoffset] [Rate][masterrate]

Create a **10-second, mono, 16-bit PCM WAV** at `S=48000`, exactly `N=480000` frames, using a trusted fixture generator. Use silence except recognisable short pulse patterns starting at source frames `96017`, `192023` and `288011`; for example, pulses at offsets `0`, `100`, `300` within each pattern. Keep amplitudes below full scale. Independently inspect the file for rate, channel count and exact frame count; record its byte hash. ### 2. Establish baseline and create the arrangement

1. Open a new empty disposable project. Stop playback, prepare zero project-start offset and master playrate 1, then save it as `reaper-capability-before.rpp`. Retain that baseline. Record track count and project metadata.
2. With the project fixed, begin a named `Undo_BeginBlock2(project)` block **before any import mutation, including tempo**. Establish **120 BPM, 4/4** before creating media. Read effective signature at zero and inspect the whole tempo map. In an empty map use `SetTempoTimeSigMarker(project, -1, 0, -1, -1, 120, 4, 4, false)`; check the result and reread it. Keep this and subsequent mutations within the error handler and paired undo block. [Tempo setter][temposet] [Effective map][timesig] [Undo rules][sdk-undo]
3. Insert two tracks at indices 0 and 1 using `InsertTrackInProject(project, index, 0)`. Reacquire them with `GetTrack`, check objects/count, and name them `A` and `B` with track `P_NAME`. Check that no effective track playback offset is present.
4. For each row below, create one item, one take and a new file source with `PCM_Source_CreateFromFileEx(path, true)`. Check each returned object and the source assignment result. Select the take. ### 3. Check geometry, sound, persistence and conversion

- Export a scratch log, not a bridge manifest: track order/name/GUID; item GUID, take GUID/name; P, length, end, offset, rate; source type/path/parents/section result/rate/channels/length/QN flag; loop/stretch/fade/timebase state; effective tempo/signature.
- Compare actual start, **end** and offset with the integer-frame expectations above. Record absolute errors in seconds and fractional frames. Measure A1-end minus A2-start separately and verify no unintended truncation, overlap or extra items.
- Check each boundary through `TimeMap2_timeToQN` and back through `TimeMap2_QNToTime`. At the chosen zero-origin 120 BPM, expected QN is `2 * seconds`; log conversion errors rather than asserting a tolerance from documentation. [Conversions][toqn] [Reverse conversion][totime]
- Inspect waveforms and audition all three pulse patterns. Confirm that each first source pulse appears at its expected item start; checking stored offsets alone cannot prove the correct source segment plays. If using an audio accessor, record its chosen rate and scope: `GetAudioAccessorSamples` documents **pre-FX** samples, not full rendered output. [Accessor][accessor]
- Save as a new result RPP, close it, reopen, reacquire all objects, repeat the logs, numerical comparisons and audition. Re-exporting after reopen is essential. Do not retain runtime pointers across reopen. [Project saving][saveproject] [Pointer validity][validateptr]
- Repeat in another empty project at **44100 Hz**, with the same P/L/O integers interpreted at `S=44100`, `N=441000`, and a newly generated 10-second source. Measure separately. This tests two matching-rate fixtures; it does not establish mixed-rate support.

### 5. Negative cases and safe failure

Prepare one isolated copy per case: missing media; non-WAV/beat-based source; empty/multiple takes; all-takes playback; source section; reverse; enabled loop; take rate 0.5; pitch shift; stretch marker; auto-stretch; manual fade; automatic crossfade; take envelope; overlapping items; folder/fixed-lane track; nonzero project origin; non-unit master rate; effective track playback offset; tempo change/ramp or non-4/4 signature. Use the matrix's getters to identify each state. Confirm preflight reports the affected object and **does not change the destination**. This is a proposed rejection policy; exact supported input belongs to ticket #9.

For a missing file, do not treat cached source properties as proof the file is readable. For a section/reverse source, log both wrapper and root properties and reject before mutation. For a tempo change, read markers as well as effective tempo at zero. These checks prevent a falsely simple offset/rate model.

Inject a caught error after the first track/item is added. Always close the named undo block. Confirm `Undo_CanUndo2` names that operation before calling `Undo_DoUndo2`, check success and compare the full relevant baseline state (tracks/items, tempo/signature and extension state), not only counts. Do not undo a different latest action. Test ordinary successful-operation undo and redo too. Source files must remain byte-identical. [Undo APIs][canundo] [Perform undo][doundo] [Undo rules][sdk-undo]

If rollback is incomplete, abandon the disposable destination and reopen the retained baseline without saving the failed state. Do not advertise atomic import. Undo does not document recovery from process termination, original-media modification or arbitrary filesystem writes. The safe initial policy is read-only source media plus a separate disposable destination, no automatic overwrite of an existing project, and no automatic save on failure. This policy is a recommendation, not a tested recovery result.
